# 成员 1：身份认证与角色权限

## 你负责什么

你负责系统的“入口和门卫”：验证账号密码、识别当前用户、区分学生/教师/注册管理员，并确保不同角色只能调用自己的接口。你的模块不负责选课业务，但其他六个模块都依赖它提供可信身份。

## 现场演示（60 秒）

1. 在登录页点击“学生”，用 `student1 / Student123!` 登录。
2. 打开“账号与权限”，点击“重新向后端验证身份”。
3. 说明学生页面没有人员管理菜单，但这只是体验优化。
4. 展示自动测试：学生请求 `/api/people/students` 得到 403，管理员请求得到 200。

## 核心代码块怎么讲

```java
return http
    .authorizeHttpRequests(auth -> auth
        .requestMatchers("/actuator/health").permitAll()
        .anyRequest().authenticated())
    .httpBasic(Customizer.withDefaults())
    .build();
```

背法：健康检查允许匿名访问，其他接口必须登录；HTTP Basic 负责从请求头取得账号密码，数据库用户服务再读取账号和角色。

```java
@RestController
@RequestMapping("/api/people")
@PreAuthorize("hasRole('REGISTRAR')")
public class PeopleController {
```

背法：`@PreAuthorize` 放在人员 Controller 类上，类内所有接口都只允许 REGISTRAR；即使学生手工拼接 URL，也会在进入业务代码前收到 403。

## 60 秒背诵稿

> 我负责身份认证与角色权限模块。系统有 STUDENT、PROFESSOR、REGISTRAR 三种角色。登录采用 Spring Security 的 HTTP Basic，账号密码由数据库用户服务校验，密码用 BCrypt 哈希保存。请求通过认证后，Spring Security 把用户名放进 SecurityContext，`CurrentUserService` 再查到账号和关联人员 ID。各业务 Controller 使用 `@PreAuthorize` 做角色限制，Service 还会做本人或任课所有权检查。因此前端菜单只是改善体验，真正的安全边界在后端。这个课程项目使用 Basic 是为了降低本机演示复杂度，正式生产环境应再加 HTTPS，并替换成会话或短期令牌。

## 必背术语

- **认证 Authentication**：确认“你是谁”。
- **授权 Authorization**：确认“你能做什么”。
- **BCrypt**：带盐的慢哈希算法，数据库不保存明文密码。
- **SecurityContext**：保存当前请求已认证用户的信息。
- **RBAC**：基于角色的访问控制。
- **401 / 403**：401 是未登录或凭据错误；403 是已登录但无权限。

## 老师追问

**问：为什么不用 JWT？**

答：本项目是本机课程演示，没有跨服务和移动端需求。Basic 配合浏览器当前会话能减少令牌刷新等代码，便于把精力放在业务规则；生产化会使用 HTTPS 和短期令牌或服务端会话。

**问：前端不显示菜单不就行了吗？**

答：不行。用户可以绕过页面直接发 HTTP 请求，所以后端必须再次授权。

**问：管理员为什么没有 linkedPersonId？**

答：管理员是业务操作账号，不对应学生或教师档案；只有需要“本人数据”的学生和教师账号必须关联人员 ID。

**问：为什么关闭浏览器标签页后要重新登录？**

答：前端把 Basic 凭据放在 `sessionStorage`，避免长期保存在浏览器，降低演示电脑上的泄露风险。
